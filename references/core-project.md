## Project Boundaries

- Classify each affected project as a private service or reusable library. For a broad workspace audit,
  do that for every member; for focused work, inspect only affected members and the shared root.
- Record every runtime role and command. A package can legitimately expose more than one long-running
  entry point even though it remains one project.
- Prefer the packaged application created by current `uv init`, a `src/<import_name>/` layout, and
  `uv_build` for a Docker-deployed service so local development and image installation use normal
  package semantics.
- Under the NGC Docker-service profile, keep `version = "0.0.0"` fixed, use the image as the sole
  deployable artifact, and do not add routine `uv build`, wheel, or sdist jobs. Apply that artifact
  policy only to the selected Docker-service profile; do not infer a deployment migration from it.
- Use `[tool.uv] package = false` and omit `[build-system]` only when the application deliberately does
  not need installation. Declare `[build-system]` for an installable project even when a private
  service never publishes distributions.
- Treat wheels and sdists as intentional artifacts only for a genuinely reusable library. Build both,
  inspect their contents, and install the wheel into an isolated environment for a smoke test.
- Keep one-off maintenance, migration, import, and audit entry points under `scripts/`. Let them
  orchestrate package APIs; do not duplicate business logic there.

## Source and Runtime Assets

- Put runtime templates, migrations, and static data inside the package or explicitly declare and copy
  them as runtime assets. Do not assume installing the Python module also installs repository-root
  assets.
- Verify every selected runtime role from the same installation mode used in deployment. Confirm that
  each role can resolve its templates, static files, migrations, certificates, and data tables.
- When changing build backends, inventory backend-specific tables and files such as
  `[tool.setuptools]`, `[tool.hatch]`, `setup.cfg`, `setup.py`, and `MANIFEST.in`. Remove or migrate
  obsolete configuration only after confirming that the active backend does not own it.
- `MANIFEST.in` is a setuptools input for source distributions. It does not copy runtime files into a
  Docker image and is not generic package-data configuration.
- Extend the generated `.gitignore` with anchored `/.env`, `/config.toml`, and `/data/`. Add
  `/.secrets/` only when the repository actually uses local mounted secret files.
- Mirror selected secret and local-state exclusions in `.dockerignore`, but never exclude a manifest,
  lockfile, source directory, or runtime asset that the Dockerfile reads. Cross-check the effective
  ignore file against every `COPY`, `ADD`, and bind mount.

## Dependencies and uv

- Declare project metadata through `[project]` and development tools through `[dependency-groups]`.
- Add and remove dependencies with `uv add` and `uv remove`. Commit `pyproject.toml` and `uv.lock`.
- Do not maintain a second hand-edited requirements file unless an external consumer requires an
  exported one. Make the export command and source lock explicit.
- Rely on `uv run` to lock and synchronize a development project automatically. Use
  `uv run --locked` in CI so stale metadata fails instead of rewriting `uv.lock`.
- Reserve explicit `uv sync` for cases where installation is the goal, especially cache-efficient
  container layers and provisioned runtime environments.
- Let packaged local development use uv's editable installation. Install packaged services in images
  with `uv sync --locked --no-dev --no-editable`.
- Bound `uv_build` to the next incompatible minor version. Preserve an intentional older range;
  otherwise use the range generated by the installed `uv init` or current uv documentation.
- Validate the lock before tool-specific checks with `uv lock --check`.

## Python and Metadata

- Declare the actual minimum supported Python in `project.requires-python`. Pin the selected local and
  service runtime minor in `.python-version`, and align CI and container images with it.
- Default new NGC projects to Python 3.14 or above. Preserve an existing project's supported runtime
  unless the user authorizes an upgrade and dependency compatibility has been verified.
- Do not add `from __future__ import annotations`; use the selected runtime's native annotation syntax.
- For a private project, add `classifiers = ["Private :: Do Not Upload"]`. PyPI rejects that
  classifier, but it does not protect other registries; omit publication credentials and workflows as
  a separate control.
- Never publish an NGC repository, Python distribution, JavaScript package, or service image to a
  public destination. In a selected JavaScript-tooling capability, set `private = true` and
  `license = "UNLICENSED"` in `package.json`.
- Prefer TOML for application and tool configuration when supported. Use YAML for formats that require
  it, notably Compose and GitHub Actions.

## Repository Instructions

- Discover the existing instruction and specification hierarchy before editing. Preserve an
  intentional hierarchy even when its filenames differ from the new-project preference.
- An NGC repository keeps its shared agent instructions in a repository-local, committed root
  `AGENTS.md`. Do not create one per subdirectory by default: add a nested file only when that subtree
  has genuine scoped differences, and state only those differences. Make required vendor-specific
  instruction files thin pointers to the shared source.
- Keep a committed `docs/` directory for durable design, architecture, decision rationale, and
  operational invariants. Do not prescribe a universal directory layout. Prefer focused documents
  that explain boundaries and why consequential choices were made; update or remove them when the
  contract changes.
- Document the minimum developer path in `README.md`: applicable uv setup, configuration copy steps,
  and only the selected commands. Mention `just` only when a justfile exists, Bun only for the
  Prettier capability, and Docker plus lazydocker only for a containerized service.
- Avoid handwritten API catalogs, configuration inventories, copied tool settings, or other
  documentation that duplicates generated or machine-readable sources. Keep commands in the
  `justfile`, numeric gates in the owning tool configuration, and architecture rules in the narrowest
  durable document. Other files should refer to those sources rather than repeat their contents.
- Use Conventional Commits for authored commits and squash-merge or pull-request titles. Do not add
  commitlint, hooks, or history rewrites solely to enforce the convention unless the repository asks
  for automated enforcement.
- Commit both `.editorconfig` and `.gitattributes`. EditorConfig guides compatible editors; it does
  not control Git. Use `.gitattributes` to normalize text to LF, and use EditorConfig plus the selected
  formatters to require UTF-8, LF, four-space indentation, and a final newline. Preserve necessary
  CRLF exceptions for Windows-native scripts.
- Preserve unrelated dirty-worktree changes and established public or persistence contracts.

## uv Workspaces

- A uv workspace has a root `[tool.uv.workspace]` table and one or more member projects. Preserve
  member `pyproject.toml` files. Decide which affected member owns each changed runtime command or
  artifact.
- In a lockfile-only Docker dependency layer, mount every member manifest needed to validate the
  workspace. When the full workspace is not present, use
  `uv sync --frozen --no-install-workspace`; after copying members, use `uv sync --locked` with the
  production groups and installation mode required by the selected member.
- Do not copy a single-project Dockerfile mechanically into a workspace. Re-check current uv workspace
  and Docker guidance before selecting cache layers, build context, or install targets.

## Profile Verification

- For every installable project, verify that the active backend recognizes the source layout and that
  no stale backend configuration creates a false sense of packaging coverage.
- For a service, validate every runtime command and required asset using the deployment installation
  mode. Do not add a distribution build merely to prove an image-based service works.
- For a library, run `uv build`, inspect wheel and sdist contents, install the wheel in isolation, and
  exercise the public import surface across the declared Python range.
- For a workspace, verify the root lock plus each selected member's commands and artifacts.

When creating or substantially replacing project metadata or root ignore files, read
[project-starters.md](project-starters.md) and select only the matching service or library example.
